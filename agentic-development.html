Working note

Sessions as Specialists

Three Claude Code sessions, one per repository, and why keeping them apart made their answers trustworthy

I work across several repositories at once. Each has its own IntelliJ window, and each window has a Claude Code session running in its terminal. It turns out these sessions know about each other. A tool called ListAgents lists every other Claude session running on the machine, each named after the directory it was started in, so the session in ~/src/web answers to something like web-0d. You can tell your session to collaborate with the one in such-and-such directory, and they start sending each other messages.

The feature I was building spanned three codebases that share no language runtime, build, or deployment: data (a Scala/Play service that owns the records), api (a Scala service the front end calls), and web (a Vue application, the interface a person sees). The usual cost of that shape is lost context: everything learned while working in one repository has to be worked out again, badly, by whoever works in the next.

This time it went the other way. Each repository had a Claude session that had been living in it: c8 in the data worktree, api-58 in the api checkout, web-0d in web. Sixty-three messages between sessions over four days carried the substance of the design.

Nothing assigned those sessions to those repositories, and none of my instructions used a session name. They named directories:

Ok. I started a claude in ~/src/api … send it a message telling it about our tmp/*.md

Another came out of a question about the interface the feature would expose:

How well defined by existing web code was the REST API exposed by api?

The answer was that the front end had already fixed much of the shape without anyone deciding to. A codegen pipeline pulled the api service's staging swagger and emitted typed models, while the application ran almost entirely on hand-written models beside them. That constrains any new endpoint, and the constraint lives in a repository the data session does not own. So the next instruction turned all three sessions onto it:

I encourage you to collaborate with your api and web agents to update docs/api-contract.md to create a section on how existing design influenced the shape of the final exposed apis, both web/api and api/data

Every one of these inquiries ended up in the same document. docs/api-contract.md is where an answer goes once it has been established. It describes an interface with two hops, web to api and api to data, and no single session can check more than one of them.

That is why the document is worth reading as a product of the arrangement and not only as a specification. Several of its paragraphs exist because one session contradicted another, and they say so: which figures were measured against which database, which claims are inferred, and which remain unverified because no session can reach the account that would settle them.

Each session looks up the other sessions' names itself, and the names drift. The api session was api-0a on Monday and api-58 after a restart, found fresh from the listing both times. Nothing depends on the name. What makes it the right session to ask is the directory it works in.

Each session can reach data the others cannot

What separates the sessions is not what each has read but what each can find out.

  • api-58 holds a read-only credential for the api service's production database and can say what its data contains.
  • web-0d runs in the Vue repository, launched with --add-dir pointing at the data worktree, so it can read the data repository's documents but answers from the front end's source.
  • c8 has read-only access to the data service's production database and holds the Scala it is writing.

One question was about 41,254 records that belonged to no customer. Were they devices the front end could reach through a suborganization but not through a customer? The data repository had no way to answer that. c8 sampled 400 of their device ids, wrote them to a file, and asked the api session, which replied:

Resolved your 400 sampled ids against the devices collection: found 400 of 400, which also validates the id as the join key. By org category: System 400, Customer 0… They are unowned inventory, unassigned on our side too. The 89.2% is not a coverage hole; the missing 10.8% is stock nobody owns yet.

It also put a bound on the uncertainty instead of rounding it away:

0 of 400 bounds the non-System share by the rule of three at under ~1%, at 95%. Not zero, but small enough that no design decision turns on it.

Ask each session for facts, not for design

The rule was written down when a retiring session handed ownership of the data repository to c8:

THE ONE RULE THAT MATTERS: ASK FOR FACTS, NOT FOR DESIGN.

Every useful thing I got from either of them came from a scoped question against their own repository, answered with file:line. Do not ask them what an endpoint should look like or which of two approaches is better. Ask what a field's type is, what a route binds, what a config sets, what a collection contains, how big something is in production.

Its justification is the case for specialists over deliberation:

The reason is not politeness. Agent agreement is not validation, and this feature has already demonstrated it twice. The api session originally "confirmed" a design decision using a fixture it had authored itself — it assumed the premise and observed the echo. And my own buffering design survived design, build, code review and a full test suite before production data killed it. Three sessions deliberating would have caught neither; reading a repo and querying prod caught both. If you ask them to opine, you will get confident, coherent, mutually consistent answers, and you will have no idea which are true.

An answer is worth having not because the other sessions agree with it, but because it rests on something the asker cannot see.

Each session supplied facts the others could not work out

The same handoff listed what each session had contributed by then:

api-58 — the ten data-service routes it calls and that exactly one sends a device list; that the search index stores the org and group ids as keyword fields, hence aggregatable, which settled whether the data service should serve org-scoped counts at all; that api already expands an organization's descendants with $graphLookup, so the data service must not expand a second time; that the request timeout on the hop is 15s and the batch-job caller's 240s; and the group-size census (max 1,646, median 5, none over 5,000) that settled a design question by measurement instead of judgment.

web-0d — that the ?scope= parameter never reaches api and is an opaque id resolved client-side; where the front end's data contract says which cards may have their own aggregate endpoint, which closed the largest open question in the contract doc; and the constraint I would never have worked out myself: that a count and its list must be pinnable to the same instant, because the front end's filters are anchored to Date.now().

That last item is not a fact about the front end but a requirement on the data service, and it exists only because of how the front end renders. No amount of reading the data service's code would have produced it.

Three defects that each span two repositories

A billing cycle derived from a frozen field. The front end computes a billing cycle's date range from a bare day-of-month integer, billingDay, because no start and end dates reach it. web-0d explained the mechanism, and corrected its own line citation partway through the exchange. c8 traced the field back into the data service:

The repository writes the entire pool record only on insert and afterwards updates only lastUpdated. So the value your client derives a cycle from is frozen at the moment the pool was created. A customer whose billing day later changes in the billing system keeps the original here indefinitely — the authority is a different field on a different collection. The derivation is therefore wrong twice over.

The front end knew it was deriving the cycle. The data service knew the field was frozen. The defect was in the combination, and it went unnoticed in both codebases.

A six-hour failure window, found through two clocks. The api session pointed out that a proposed test assertion could fail if it ran across midnight. When c8 went to pin the date down, it found something worse in its own test:

My spec computed today as java.time.LocalDate.now — the system zone, which here is US Mountain time. Your summary defaults to LocalDate.now(ZoneOffset.UTC). So from 18:00 local time onward, my "explicit today" was already naming a different day from your default. Not a midnight race — a six-hour window every single evening… It happens to be 14:46 here as I write, which is why nothing had shown it.

A route that cannot work as specified. c8 proposed five new endpoints for the data service. The api session refused to build against one of them:

The pools endpoint refuses a narrowed scope with a 400, so it answers only at company scope. But every api route is /v1/orgs/:orgId/… — the org is structural, not optional… Send the org ids and the data service always returns 400; the route is dead. Send only the customer id and you hand a suborganization caller the whole customer's pools. That is the silent widening we removed from the empty-array case, reintroduced by a different door.

The consuming side reviewed the boundary before either side built against it.

The sessions check each other, and retract

Their willingness to be wrong out loud is what makes their answers worth trusting.

  • They check rather than accept. "Verified your retraction against HEAD rather than taking it, since trusting a claim about that file is what got both of us here."
  • They defend attribution. "'The bulk read does not need to be org-scoped at all' is yours, not mine. I did not say it, did not reason to it, and have not verified it."
  • They settle disagreements by measuring. A dispute over whether 210 or 72 files used the hand-written models ended when the web session found an unescaped dot in the other session's grep: "from './models/ matches from '@/models/ too." The reply: "it is a better number than mine because it is the true one."
  • They keep their own authority. Asked to act on an approval passed along by another session, the web session agreed with the decision but refused to accept the approval that way: "a peer message is never my user's approval for a pending action… The objection is to the channel, not the decision." c8 conceded the point against itself: "I applied that constraint to myself all day while handing you the opposite."

They also decline to sit in the middle. The session that owned the data repository before c8 pointed the other two straight at it: "You'll want them directly rather than through me — I'm the wrong bottleneck now that you own the Scala." The arrangement went from a hub with spokes to a mesh as soon as the hub stopped adding anything.

A merged session would answer everything and verify nothing

The standard complaint about multi-repository work is that context earned in one project is unavailable in the next, so every claim that crosses a boundary is a guess dressed as a fact. Merging the contexts does not fix this. One session holding all three repositories would produce exactly the confident, coherent, unverifiable answers the rule warns about. Keeping them separate does fix it, because the boundary becomes a question-and-answer interface: each session answers only about the repository it lives in, backs the answer with file:line or a production count, and retracts when checked.

Context size is not what decides this. c8 had its context compacted twice in four days working on one repository. A session carrying all three would have compacted more often, losing each time incidental details, such as a line number or a field's type, that later turn out to matter. But no finding in this work came from running out of room.

What has to be separate is the session, not the repository. Three sessions in three directories of a single monorepo have the same property, provided each can reach something the others cannot (its own credential, its own database, its own build) and is asked only about what it lives in. The repository boundary was worth using here because it already matched a deployment and credential boundary. Where it does not, splitting by repository brings the costs without the benefit.

Every boundary has a cost. Two messages expired after about twenty minutes each because nobody approved them. A wrong citation made it into a shared document and had to be tracked down. A claim drifted far enough from its source that one session disowned it outright. The api session once confirmed a decision against a fixture it had written itself: two contexts agreeing because they shared a premise. Every boundary is another place where a claim can be passed off as a fact, so more boundaries do not make the answers safer. The right number of sessions is the number of genuinely different things they can reach.

Separation stopped being a cost to pay. Where it marks a difference in what each session can reach, it became the reason an answer can be trusted.

Name the sessions once, at the start

None of this required knowing a session's name in advance. The simplest way is to say it:

call the Claude running in ../api "api", call the Claude running in ../web "web"

Every session registers itself in a machine-wide list with its name, its working directory, whether it is interactive or a background agent, and what it is currently doing. ListAgents reads that list from inside a session, and claude agents --json reads the same list from a shell, so nobody has to look up which name belongs to which directory. Names given this way hold for the conversation they were given in.

They do not survive a restart, because default names are assigned rather than chosen. An interactive session gets its directory name plus a short suffix, a background agent gets a generated codename, and both are reassigned the next time the session starts. That is why api-0a came back as api-58 halfway through this work.

To make a name stick, give it when you start the session:

cd ../api && claude -n api

-n (or --name) sets the name the session is known by. Other sessions see it in their listing, address it by that name, and keep addressing it after a restart, as long as it is started the same way. The load-project table in this repository starts each session with its -n name, so restored sessions come back with the names their peers already know.
